# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

BoostBox is a Clojure API for storing and retrieving Podcasting 2.0 payment metadata (boostagrams). Podcast apps POST boost metadata to `/boost`, receive a short URL, and that URL can later be fetched to retrieve the full metadata via an `x-rss-payment` HTTP header for Lightning invoice descriptions.

## Build & Development Commands

This project uses Nix flakes for all build/dev/test tooling.

### Enter dev environment
```sh
./dev.sh
```

### Available scripts (inside dev shell)
Run `scripts` to list all available commands. Key ones:
- `scripts repl` — Start NREPL on 0.0.0.0:9998
- `scripts tests` — Run full test suite (starts MinIO for S3 tests)
- `scripts watch` — Run tests in watch mode
- `scripts format` — Format all code (Clojure, Nix, Markdown via treefmt)
- `scripts build` — Build with Nix
- `scripts outdated` — Check for outdated dependencies
- `scripts lock` — Update lock files

### Run tests outside dev shell
```sh
./test.sh                    # Full suite with MinIO via Nix testenv
clojure -M:test              # Direct Clojure test runner (no S3 tests)
clojure -M:test --focus boostbox.nwc-test   # One namespace; repeat --focus for more
```

### Build and run
```sh
nix build                    # Compile via clj-nix
./result/bin/boostbox        # Run compiled binary

clojure -T:build uber        # Build uberjar (no Nix required)
java -jar target/boostbox.jar # Run uberjar
```

### Format check (CI)
```sh
nix flake check              # Runs treefmt formatting check
```

## Architecture

### Source Layout

- `src/boostbox/boostbox.clj` — Main application: config, storage, routes, middleware, HTML rendering, server startup (single-file monolith with `(:gen-class)`)
- `src/boostbox/ulid.clj` — Custom ULID encoding/decoding using Crockford Base32
- `src/boostbox/images.clj` — Loads the page artwork (favicon, background) from `resources/` and names each by a content-hashed `/assets/…` path
- `src/boostbox/safefetch.clj` — The one door for outbound HTTP to a URL we did not choose. Shared by the bot (boost links, feeds) and the web app (banner art)
- `src/boostbox/banner.clj` — Draws the 1200×300 PNG a boost note carries, served at `GET /og/boost.png`
- `resources/fonts/` — The bundled display face for that banner, plus its OFL licence
- `resources/v4vbox.jpg` — Background image for the homepage and boost pages
- `resources/favicon.png` — 64×64 favicon
- `test/boostbox/boostbox_test.clj` — All tests (unit + integration, both storage backends)

Boost bot (separate process, same uberjar — see "Boost Bot" below):

- `src/boostbox/nostr.clj` — BIP-340 schnorr, NIP-01 canonical events, NIP-04, NIP-19 bech32. Zero third-party deps beyond BouncyCastle
- `src/boostbox/relay.clj` — Nostr relay websocket client over aleph
- `src/boostbox/nwc.clj` — Nostr Wallet Connect (NIP-47) client and boostagram extraction
- `src/boostbox/boostagram.clj` — blip-10 → BoostMetadata mapping, note tags, note text, banner URL (all pure)
- `src/boostbox/feed.clj` — Reads two things out of an RSS document: the npubs the feed declares, and a cover image. Pure
- `src/boostbox/applinks.clj` — Deep links back into the app a boost was sent from, built from the foreign keys a boostagram already carries. Pure
- `src/boostbox/podcastindex.clj` — Resolves a `<podcast:guid>` to a feed through the Podcast Index API. Optional: no credentials, no behaviour
- `src/boostbox/nostrbot.clj` — `(:gen-class)` entry point: config, cursor/dedupe state, poll loop
- `test/resources/bip340-vectors.csv` — unmodified official BIP-340 vectors from bitcoin/bips

Operator scripts (all read-only against the wallet, all prompt for the NWC string with echo off rather than taking it as an argument, where `ps` would expose it):

- `scripts/bot-setup.sh` — validate an NWC connection string and mint the bot's Nostr key into a 0600 file, printing only the npub
- `scripts/nwc-inspect.sh` — dump what the wallet actually reports for recent payments: `description`, TLV types, whether a boostagram can be extracted, and each payment's skip reason. The first thing to run when the bot sees payments but publishes nothing. It reads only the payment itself and never fetches a boost link, so an LNURL boost shows `reason=:no-boostagram` here even though the bot would publish it — check the `boost link` line for those
- `scripts/bot-local.sh` — run the bot locally in dry-run with backfill, against the same wallet as the deployed one. Its cursor goes to a temp dir, so the deployed bot's state is untouched
- `scripts/pi-check.sh` — check a Podcast Index key against one feed guid before setting it on the deployed bot: resolves the guid, then reads the feed behind it and reports the cover and npubs the notes would actually get

### Key Patterns

**Storage protocol:** `IStorage` protocol with two implementations:
- `LocalStorage` — filesystem, stores as `{root}/YYYY/MM/DD/{ulid}.json`
- `S3Storage` — AWS/MinIO via `cognitect.aws`, same path structure

**ID generation:** UUIDv7 → ULID (26-char Crockford Base32). The ULID embeds a timestamp used to derive the storage path.

**Validation:** Malli schemas for request/response coercion, integrated with reitit routes.

**HTTP stack:** Aleph server → reitit router → middleware chain (virtual threads, correlation IDs, MuLog logging, body size limiting, CORS, muuntaja content negotiation, Malli coercion, Swagger).

**HTML rendering:** Chassis (hiccup-like DSL) for homepage and boost viewer pages. The homepage displays one card per boost — not per stored record, see "A boost is a `group`" below — overlaid on a fixed background image, each card a box of links ending in its leg list. Shared helpers (`boost-detail-rows`, `boost-metadata-row`, `format-sats`) are used by both the homepage cards and the individual boost viewer page.

**Chassis text escaping (footgun):** Chassis HTML-escapes string children by default, including inside `<script>` and `<style>`. Any inline JS containing `<`, `>`, or `&` (e.g. `i<n`, `a<<5`, `x&0xff`) becomes a syntax error when rendered as `[:script some-js-string]`. Wrap inline script/style payloads in `(html/raw ...)` — see how `npub-resolve-js` is injected at both call sites.

**Client-side npub resolution:** `npub-resolve-js` is an inline JS blob injected on both homepage and boost-view. It walks text nodes for `npub1…` (optionally `nostr:`-prefixed), replaces them with a truncated `<span class="npub-ref" data-npub="…">`, then fans out a `kind:0` REQ in parallel across `wss://relay.damus.io`, `wss://nos.lol`, and `wss://relay.primal.net`. First relay to return a profile with `display_name`/`name` wins and closes the other sockets. No server-side Nostr code — all resolution is client-side. If you add another spot that renders an npub, no extra work is needed as long as it ends up in a text node within `document.body`.

**Page artwork is served by URL, never inlined (`boostbox.images`, `asset-handler`).** Every page used to carry the favicon and background as base64 `data:` URIs — 3.65 MB around a 9 KB boost, which gzip cannot shrink. The homepage links every boost page, so each crawler pass paid that thousands of times: **96 GB of Railway egress in one billing period, 44% of the bill.** Each image now lives at `/assets/<name>.<sha256 prefix>.<ext>`, served `immutable` for a year; the hash is in the path, so replacing a file changes its URL rather than serving a stale copy. `pages-link-artwork-instead-of-inlining-it` fails if a `data:image` comes back. Raw bytes loaded through `io/resource` have no size limit — the old `.b64` files existed only to keep large string *literals* out of AOT class files. The `build.clj` copies both `src/` and `resources/` into the uberjar.

**The homepage is rendered once, not once per request (`page-cache`, `cached-page`).** `list-all` reads and parses every stored boost, and a crawler burst used to do that once per concurrent hit — the web app's memory peak, and one that grew with the boost count. The rendered page is now kept as UTF-8 bytes per sort order for `homepage-ttl-ms` (60 s), and `POST /boost` clears it, so a new boost shows at once. Three details are load-bearing. Concurrent misses share one render: the entry is a `delay` installed *before* storage is read, which is also what makes clearing it race-free. The cache is built in `serve`, **outside** the handler factory, because in DEV reitit rebuilds the handler on every request and a cache inside it is never hit — the tests run DEV, so `homepage-is-cached-until-a-boost-is-posted` catches a cache moved back inside. And `homepage-sort` folds any unknown `sort` into `date`, because a cache keyed by a caller-chosen string is an unbounded map. A render that throws is not cached. A write that bypasses this process — a hand edit on the volume — shows within the TTL, and so does a REPL edit to the page's own code in DEV (or POST a boost to see it at once).

**A boost is a `group`, not a record (`one-card-per-boost`).** BoostBox stores one record per payment *leg* — an app POSTs once per LNURL leg, the bot once per keysend leg it receives — and the legs of one boost share `group` (blip-10's `uuid`). The homepage draws one card per group, from the first leg exactly as stored; on 2026-09-26 that was 1,463 cards from 2,983 records, and every count and sat total had been counting each boost once per leg. **Never merge fields across legs:** each is payer-written, so a merge lets anyone who learns a group id write onto another boost's card. The other legs are *listed* under the card instead (`::legs`, `boost-legs`) — recipient, sats, and a link to each leg's record — because the homepage is where the operator checks who got paid. The list says "Legs recorded", not "paid": a record is not a payment, and a keysend leg the app never POSTed is simply absent. **A leg joins its card only within `leg-window-ms` (60 min) of the first leg, dated by its server-minted ULID**, never by a payer-written field. The bot files a keysend under whatever `uuid` its payer wrote, so a few sats can claim any group id; the window keeps such a leg off an older boost's card (the slowest real boost on 2026-09-26 took 54 minutes, the median 14 s). A leg outside it, or one whose id is not a ULID, is a boost of its own. **Every card lists its legs, a boost of one record as its one leg:** the card's amount is the whole boost's, and half the cards are one record of a split boost whose other legs went by keysend, so only the leg line says who that record paid and how much. A card is therefore not one `<a>`, because links cannot nest: its rows link to the first leg and each leg line to its own record. The bot must carry `uuid` through as `group` (`bg/->boost-payload`), or its keysend leg shows as a boost of its own beside the app's LNURL legs. **It only started doing so on 2026-09-26 (#36):** every keysend leg it stored before then has no `group`, so those boosts still show as two cards — the app's record and the bot's — and no code can rejoin them, because the `uuid` was never written down. When one boost shows as two cards, look for a `group` on the bot's record before suspecting the collapse. `/boosts` and `/boost/:id` stay per record.

**BOLT11 description:** `rss::payment::{action} {url} {message}` format, truncated to 639-char limit.

**Boost Bot:** A second process — `java -cp boostbox.jar boostbox.nostrbot` — that watches a Lightning wallet over NWC, stores incoming boostagrams via `POST /boost`, and republishes them to Nostr as `kind:1` notes with NIP-73 `i`/`k` tags. It is deliberately NOT a route on the web app: it holds an nsec and a wallet credential, and it is a long-lived loop with at-least-once delivery. `build.clj` compiles everything under `src/`, so its `(:gen-class)` lands in the same uberjar automatically — no build changes needed to add an entry point.

**Bot identity is two events, not one (`BBN_PUBLISH_PROFILE`):** `kind:0` gives the npub a name; the NIP-65 `kind:10002` relay list is what makes it findable, since without one a client cannot know which relays hold the bot's notes. Both are one-shot and opt-in. The relay list marks every relay `write` — the bot publishes and reads nothing — and never includes the wallet relay, which is reachable only with the NWC credential.

**Nostr crypto (do not hand-edit casually):** `boostbox.nostr` implements BIP-340 signing on BouncyCastle's curve math. It is verified against the official BIP-340 vectors in `test/resources/bip340-vectors.csv`, including the 10 failure cases. Any change to the signing, `lift-x`, or tagged-hash code MUST keep those green — a subtly wrong signature is silently accepted by nothing and rejected by every relay.

**NIP-01 serialization is hand-written on purpose:** NIP-01 escapes exactly seven characters and emits everything else — forward slashes, non-ASCII — verbatim. jsonista escapes a different set, which yields a different event id and therefore an invalid signature. Never swap `boostbox.nostr/canonical-event` for a general JSON encoder.

**Three metadata sources (`nostrbot/tx->boost!`):** TLV `7629169` first, then the wallet's parsed copy, then a *boost link* in the payment description, fetched via its `x-rss-payment` header. The third is not a fallback for odd cases — an LNURL payment cannot carry a TLV at all, and that is how most Podcasting 2.0 apps pay a lightning address, so for a bot paid at one it is the **common** path. A link-sourced boost already has a BoostBox record (that is where the link came from), so `publish-boost!` reuses its url and id instead of POSTing a duplicate.

**A transaction that publishes nothing says why (`nwc/transaction->boost`, `nostrbot/tx->boost!`).** Both answer either a boost or `{:skip <reason>}`, never nil — callers test for `:boostagram` — and `poll-once!` puts a `:skipped` breakdown on the poll line. The reasons are not interchangeable: `:no-boostagram` is an ordinary payment and `:not-a-boost` normally a stream, both expected, while `:tlv-unreadable` and `:boost-link-unreadable` are defects. **Only the ones worth looking up are narrated** (`narrate-skip?`): an ordinary payment and a stream are constant traffic on a wallet in a podcast's splits and would bury the rest, so they are only counted. **A boost link that yields nothing must stay `:boost-link-unreadable`**, never fold back into the TLV path's `:no-boostagram` — that reason is never narrated, and for a bot paid at a lightning address the link is the path most boosts take. There is deliberately no "decoded but did not parse" reason: `decode-tlv-value` only accepts a JSON object and `bg/normalize` turns any object into a boostagram, so it cannot occur. A skip carries the payment hash, so a missing boost is searchable by the id the wallet shows, and `first-sighting!` writes that line once per hash per process — a poll re-reads the newest transaction and everything behind a held cursor, and would otherwise repeat it every interval. This exists because all of these used to be the same nil against a poll line that only counted, so a boost that went missing left no trace and diagnosing one meant asking the payer to send their TLV by hand. The one remaining silent case is a boost link refused by `:boost-link-origins`, which reads as `:no-boostagram`; it only arises when an operator has named origins.

**A BoostBox record does not prove a payment happened.** An app POSTs the metadata *first* and pays *after*, so the record of a payment that failed stays on tardbox looking exactly like one that settled. Some apps POST only as a fallback: bullishBoosts tries keysend whenever the blip-10 JSON will not fit the recipient's LNURL `commentAllowed`, and creates a record only after that keysend has failed — for it, a record is itself a sign that something already went wrong. So when "boost X never arrived", do not start with tardbox, the bot or Helipad. List the records that share X's `group` (the legs of one boost) and find a leg whose wallet you can see: a leg paid to the bot's own address (`boostr@getalby.com`, on the same node as `chadf@getalby.com`) belongs to the same boost, so if the bot's poll lines never see it, that app's payments to that node did not settle. It says nothing about legs paid to other nodes. Only the recipient's wallet can say whether money arrived. The case that taught this, on 2026-09-26: bullishBoosts 0.56.1 turned a Podhome feed's `customKey="lnurl_callback"` (Podhome's way of attaching an LNURL callback, not a TLV type) into a keysend record, LND refused it with `no custom records with types below 65536 allowed`, and the fallback legs to that node never arrived either. 0.56.2 drops any `customKey` that is not an integer ≥ 65536.

**One wallet, many shows: the recipient filter (`BBN_RECIPIENT_NAMES`, `bg/recipient-match?`).** Every feed MSP 2.0 (musicsideproject.com) builds carries a `MSP 2.0` support split to `chadf@getalby.com`, which lands in the node's *main* wallet alongside every other split the node is in. A second bot process reads that wallet read-only and publishes only boostagrams whose `name` is `MSP 2.0`. It filters by **recipient, not feed**: MSP feeds are hosted anywhere (the first one seen was on phafe.com), and trimmed, case-folded name equality is exactly MSP-2.0's own `isMspSplit`, so the two systems agree about which payments are MSP's. The recipient check runs **before** the action check and yields `:other-recipient`, which is counted and never narrated — on a shared wallet it is constant traffic, and letting another show's boost fall through to `:not-a-boost` would narrate every one. `BBN_ACTIONS` widens what publishes: v4vmusic sends `"auto"` for its per-song automatic boosts, which is why `BoostMetadata` accepts `auto` beside `boost`/`stream`. Both variables default to today's behaviour, so the Boostr bot is unaffected by them.

**Reading a busy wallet over NWC has two limits, and both fail as a silent timeout (`fetch-transactions!`).** Every reply has to fit in one encrypted event the relay will carry, and a wallet in many shows' splits carries a ~2 KB boostagram on nearly every payment: relay.getalby.com passed a page of 20 (39 KB) and silently dropped a page of 50, so `transactions-page-size` is 10. Separately, the relay stops answering after about sixty requests a minute — a walk at ~2.5 pages a second went silent on its 61st request, while single reads of the very same transactions went through once the minute had passed — so a walk longer than one page waits `page-interval-ms` between pages, and `read-page!` waits out a timed-out page (`timeout-retry-ms`) before asking again. It retries **only** a timeout (`:timeout?` in `call!`'s ex-data): a wallet error is a refusal and will not change. Neither limit shows on the Boostr sub-wallet, which reads one short page a minute; both bite on the first backfill of a main wallet, where a failed poll restarts the same walk from the same cursor and fails the same way, forever.

**A note is dated when the boost was paid, not when it was published (`build-note`).** `created_at` is the payment's `settled_at`, clamped to now. Live, the two are a minute apart; on a backfill they are months apart, and stamping months of boosts "now" lands all of them in followers' feeds at once. The clamp matters: a wallet clock running ahead would date a note in the future, and relays refuse those.

**The state file is the bot's only memory, and losing it is silent (`check-state-durability!`).** The cursor and the de-duplication set live together in `nostrbot/state.json`. With no cursor the bot starts from now, so every boost received while it was down is dropped unpublished — right for a new bot, data loss for a restarted one. `check-state-durability!` refuses `BB_STORAGE=FS` outside `DEV` unless `BBN_ALLOW_EPHEMERAL_STATE` asserts the path is a mounted volume, and `::ephemeral-state-permitted` then says so at startup; `::no-cursor-window-dropped` fires whenever the bot starts with no cursor and no backfill. Those two lines together are what explain a boost lost across a restart. **Never recover from a lost state file by backfilling** (`BBN_BACKFILL_SEC`), and never make the bot do it automatically: the de-duplication set went with the cursor, so a backfill re-announces every boost in the window that was already published, as notes nobody can edit. Making that safe needs a dedupe that outlives the state file.

**Outbound fetches to a URL we did not choose go through `boostbox.safefetch`, and it is a security boundary — read before touching it.** Three callers now: the boost-link `HEAD` (a URL from a payment description), the feed read (a URL from a boostagram), and the banner's artwork fetch (a URL from a query string). All three are attacker-controlled. Three separate things guard them, and they are not interchangeable:

1. The **caller** decides a link's **shape** — `bg/boost-link` for a boost link: https only, and within `:boost-link-origins` when that is set. It is *not* the protection: the default is to accept any public https origin, because apps POST to whichever BoostBox they run and a podcaster adding this bot as a split cannot enumerate those in advance. An allowlist here would skip almost every real boost.
2. `safefetch/public-addresses` decides the **destination** — resolves the host and refuses loopback, link-local, RFC1918, CGNAT, IPv6 ULA, multicast and reserved space. This is the check that matters.
3. `safefetch/request-pinned!` opens the socket **to the address already checked**, rather than handing a hostname to an HTTP client that would resolve it a second time. That second lookup is the DNS-rebind window. SNI and endpoint identification stay on, so pinning the address does not weaken certificate validation.

Redirects are refused (a public host answering 302 with a private address is the standard way around an address check), headers read under a byte cap, and a body **only** under an explicit one. A body over the cap is **refused, never truncated** — a half-read feed parses as a different feed, and its npubs become `p` tags. `fetch-pinned!` is the whole guarded GET in one call and answers `nil` for every failure, because none of the reasons change what a caller does next. Do not "simplify" any of this back to `http/get` on a URL — it looks like an over-complicated way to make one request, and every part of it is load-bearing.

**Payer-written text is bounded (`boostagram/clean`):** message, titles and names all reach a `kind:1` note signed by the bot's key, and every one of them is written by whoever paid. `normalize` strips control characters and caps lengths there, at the boundary, rather than at each use.

**The note format is boostmebitch's, deliberately (`boostagram/->note-content`, `->nip73-tags`).** Both apps publish Podcasting 2.0 boosts as `kind:1`, so a reader scrolling a feed should see one kind of card whichever app published it. The layout mirrors `lib/nostr/boost-notes.ts` — `⚡ Boost ⚡`, the message, `{sender} boosted {n} sats → {show}`, `📻 {episode}`, the banner URL — and the tags mirror its emission order. **The BoostBox permalink is deliberately not in the body**, unlike BMB's: it stays on the `r` tag, where a client wanting the full metadata still finds it. Clients render a bare link as a preview card, and a card whose entire content is a boost id sits under every note saying nothing the note has not already said. The app link is the one a reader wants — it goes to the episode, not to a record of the payment. **Two of them answer different questions and must not be merged:** `client` is NIP-89, the app that *created and signed* the event, which is always this bot (a reader's client renders it as "via …"); `app` is the app that *sent* the boost. Putting the paying app in `client` attributes the bot's own note to software that never signed it. `note-sats` is deliberately not `format-sats` — the note matches BMB's plain, always-plural string, `format-sats` groups thousands for the HTML pages, and a note and a card disagreeing about one payment is worse than either choice.

**The body is BMB's; the tags are a superset (`nip73-id-tags`).** The parity that matters is what a *reader* sees, and a reader sees the body — so the body stays BMB's line for line, and pass-through data goes in tags, which cost a reader nothing. Three additions beyond BMB's set, and none of them is decoration: `remote_feed_guid`/`remote_item_guid` become their own `podcast:guid`/`podcast:item:guid` `i` tags, because a `<podcast:remoteItem>` boost settles on the host feed's splits while the thing actually boosted lives in another feed — without them that reference is unrecoverable and the remote feed's own audience can never query for the boost; `app` carries the sending app's version as a third item; `recipient` names which split this note announces. A remote guid is validated by the *same* validator as its local counterpart, for the reason in the feed-vs-item note above. `k` is emitted once per **kind**, not once per id, and ids are de-duplicated — apps that send a remote item routinely repeat the host guid in both fields.

**The booster gets a `sender` tag, never a `p` (`boostagram/sender-npub`).** When the paying app knows who paid — BoostMeBitch sends `sender_npub`, and its `sender_id` is the same key in hex, though for every other app `sender_id` is an app-internal string, so only an exact 64-char hex value is read that way — the npub is round-tripped through NIP-19 to validate and normalize it, then emitted as `sender`. It is **not** a `p` tag, and that is the whole point: `sender_npub` is payer-written, so a `p` would let anyone who pays one sat put this bot's signed note into a stranger's mentions, repeatedly, permanently, and undeletably. The `p` tags on a note come only from the feed, where a podcaster declared their own npub in their own RSS.

**The app link's origin comes from `boostbox.applinks`, never from the boost.** The note's one departure from BMB's body is a line pointing back into the app the boost came from — the episode where the app routes on a key a boostagram carries, the show otherwise. The patterns are from `nathangathright/podcast-platform-links`, and only the ones buildable from a boostagram are in the table: anything needing an Apple id or a platform-internal episode id is omitted, because a link that cannot be built is worse than no link. **The security property is that the origin is always a literal in the table.** Every interpolated value is payer-written, so each is either shape-checked (`podcast:guid` as a UUID, the Podcast Index ids as digits — they land in a path segment, where an arbitrary string walks out of it) or encoded into a safe alphabet (base64url, hex, percent). A payer choosing their own `app_name` picks which row is used; they cannot introduce an origin that is not written there. This is also the only reader-facing use of `feedID`/`itemID`, which are the Podcast Index show and episode ids and were parsed and discarded until now.

**One app's boost teaches the next where a feed lives (`nostrbot/remember-feed`).** Apps disagree about what they send — BoostMeBitch sends the feed address, Castamatic sends only the guid — so `feed_guid → feed URL` is memoized in the bot's state file whenever a boost carries both, and filled back in when one carries only the guid. Without it a show boosted solely from an app that sends no address never gets cover art or the feed's `p` tags, and nothing logs a reason. The memo is cleared rather than evicted when full, exactly as `feed-cache` is: it is an optimization, and rebuilding costs one boost per feed. Only an address `safefetch/fetchable-url?` accepts is stored, so recalling one never hands `safefetch` something it must refuse.

**Three sources for a feed address, cheapest first (`nostrbot/resolve-feed`):** what the app sent, what the memo learned, then the Podcast Index. The memo alone has a warm-up hole — a show boosted *only* from apps that send no address never gets art or `p` tags, because nothing else maps a guid to an address — and `boostbox.podcastindex` closes it on the first boost. An address the API returns is memoized like any other, so a show costs one lookup rather than one per boost. **It is deliberately not on `safefetch`:** that machinery is for URLs a *payer* chose, and this origin is a literal in the namespace with a UUID-checked guid as its only payer-written part; routing it through an SSRF guard would imply the origin were in doubt. Credentials are optional and everything degrades to the memo without them. Two traps: the API rejects a generic `User-Agent` with a **403 whose body talks about user agents, not credentials**, which reads exactly like an auth failure; and it answers `"feed": []` rather than omitting the key on a miss, so an empty vector must read as nothing found. The API's artwork is used only as a fallback behind the feed read, which can carry the *episode's* art where the API only knows the show's.

**`/og/boost.png` is a PERMANENT PUBLIC CONTRACT — never rename the path, a parameter, or the `.png`.** Every boost note writes that URL into a signed `kind:1`, which cannot be edited, so a tidy-up blanks the picture on every note ever published, all at once. Add parameters; never repurpose one. The extension is in the *path* because a Nostr client decides whether a bare URL is an image before it fetches it. The names are boostmebitch's so the two routes are interchangeable. Three places must keep agreeing: `banner/render`'s size, `boostagram/banner-dimensions` (the `imeta` tag's `dim`), and `boostagram/banner-url`'s parameter names. The wordmark on the picture and the `client` tag on the note both default to `boostagram/default-client-name` — the banner is served by the web app but only ever appears on the bot's notes, and one note carrying two names for the same publisher is worse than either name.

**The banner needs a font, and a missing one fails as a blank picture, not an error.** `eclipse-temurin:21-jre-alpine` ships no fonts at all. The face is bundled in `resources/fonts/` and loaded with `io/resource` — **not** `Class.getResourceAsStream`, which resolves against the calling class's loader and cannot see the jar from `java.awt.Font`; it returns nil, the fallback hides it, and the banner draws in the platform sans while claiming otherwise. The Dockerfile adds `freetype` and `fontconfig`, and `-main` sets `java.awt.headless` in-process so the Nix and bare-jar paths get it too. `banner-test` asserts the bundled family is the one actually in use.

**The feed scan is linear, and that is a rule, not an implementation detail (`boostbox.feed`).** Walk a document with `find-tags`/`find-blocks`, never a `[\s\S]*?` regex, and read an attribute with `read-attr`, anchored on `(?:^|\s)` — `\bnpub` matches inside `x-npub`, so a decoy attribute is read as the real one. `find-blocks` locates every close tag **once** and binary-searches; scanning for the close from each open tag is the quadratic shape, and it does not announce itself — 200k unclosed `<podcast:txt>` opens measured **72 s** that way and 30 ms this way, on a document a feed can serve by accident, on the thread the poll loop runs on. `feed-test` pins it.

**The feed URL is read and never rendered.** `:url` on a boostagram is written by whoever paid us. Fetching it behind the address check is fine; printing it in a note this bot's key signs, or emitting it as an `r` tag, puts an attacker's link under the bot's identity. The note's only link is the BoostBox permalink. A feed read failing for any reason answers `nil` and the note publishes without a picture or `p` tags — a feed being down must never stop a boost being announced.

**Two schemas, one repo:** `boostbox.boostbox`'s `BoostMetadata` and blip-10 name the same things differently — `feed_guid`/`guid`, `item_guid`/`episode_guid`, `feed_title`/`podcast`, `item_title`/`episode`, `recipient_name`/`name`, `position`/`ts`, `group`/`uuid`. Apps built on the BoostBox spec send the former; `normalize` accepts both spellings of all seven, blip-10 winning ties. The feed address is an eighth and the nastiest: blip-10 calls it `url`, BoostMeBitch sends `boost_link` — a name that means a *BoostBox permalink* everywhere else in this repo — so `url` is read first and `boost_link` only as a fallback. Nothing decides it really is a feed; `feed-context` hands it to `safefetch` like any other payer-written URL and a non-RSS document reads as no feed. Getting this one wrong is silent and expensive: with no feed address there is no feed read, so the banner loses its cover art and the note loses every `p` tag, and nothing anywhere logs a problem. Any new field needs the same treatment or it silently reads as nil for half of real traffic.

**Boostagram GUIDs:** the blip-10 payload lives in TLV record `7629169`. Read the *raw* record, not a wallet's pre-parsed copy: Alby Hub's `Boostagram` struct keeps `feedID`/`itemID` but drops every GUID, and NIP-73 needs the feed GUID (a UUID). `boostbox.nwc/extract-boostagram` encodes this preference.

**blip-10 value traps (beyond the naming above):** `ts` is **seconds into the episode**, which maps to BoostBox's `position`, not its `timestamp` — the wall-clock time comes from the payment's `settled_at`. Apps do get this wrong: bullishBoosts 0.56.2 sends the current unix time as `ts`, and `normalize` stores it as is, so its records carry a `position` near 1.79 billion seconds. Nothing rejects it today, and it is cosmetic — no note or homepage card renders `position`; only the boost page's raw JSON shows it — but a sanity bound, if one is ever wanted, belongs in `normalize` rather than at each use. `value_msat` is only this split's share; `value_msat_total` is the whole boost, and it is **frequently absent** (Alby's parsed struct drops it, single-recipient splits never set it) — every use of it needs a `received-msat` fallback, or the note headline reads "0 sats" and `BBN_MIN_SATS` silently drops real boosts.

**Feed guid vs item guid (`boostbox.boostagram`):** they are validated differently and must stay that way. `<podcast:guid>` is defined as a UUID, so `valid-feed-guid?` rejects everything else — a malformed `i` tag pollutes the global NIP-73 index forever. An episode guid is the RSS `<item><guid>`, an arbitrary string (usually a URL), so `valid-item-guid?` only rejects blanks and absurd lengths and the value is **not** lower-cased. Tightening the item check to UUIDs drops episode tags for almost every real feed.

**Storage root is shared (`boost-key?`):** the nostrbot keeps its cursor at `nostrbot/state.json` under the same FS root / S3 bucket the web app reads. Both `list-all` implementations filter through `bb/boost-key?`, which matches only `.../<26-char ULID>.json`. Any sidecar file added to the storage root must not be listable as a boost — a plain `*.json` filter renders it as a phantom boost card on the homepage.

**Configuration:** All via environment variables (see README for full table). Key vars: `ENV`, `BB_PORT`, `BB_BASE_URL`, `BB_STORAGE`, `BB_ALLOWED_KEYS`.

### Testing

Tests use Kaocha with cloverage for code coverage. The `run-with-storage` helper runs integration tests against both FS and S3 backends. S3 tests require MinIO (started automatically by `./test.sh` or `scripts tests`). Set `BB_REAL_S3_IN_TEST=1` to enable real S3 tests.

Private functions are tested through their var (`#'bot/first-sighting!`), as `nostrbot_test` does throughout. mulog's `u/log` is a macro and cannot be stubbed with `with-redefs`, so a decision about *what to log* belongs in a plain predicate that a test can call — `narrate-skip?` is the pattern — rather than inline around the log call.

### Deployment

- **Two Railway projects, both deploying this repo's `main`:** the web app is service `boostbox` in project **`tardbox`**, the bot is service `boostbox` in project **`boostr`**. With the CLI, `railway link -p <project> -e production`, then `railway deployment list -s boostbox` and `railway logs -s boostbox -n 40 <deployment-id>`; `railway deployment list --json` → `meta.serviceManifest` is the config a deployment actually ran with, which is the thing to check when a setting seems not to apply.
- **Both services are configured in the Railway dashboard, and the repo holds no Railway config file.** Railway deprecated config-as-code: `railway.toml` stops being read on 2026-12-01, and since 2026-08-28 a service that never used one cannot opt in. **Do not add a `railway.toml` back** — while one exists it locks every dashboard field it names ("set in railway.toml"), and on the cutoff it silently stops applying, taking those settings with it. The dashboard's builder reads `Railpack` on both services and that is fine: Railway detects the root `Dockerfile` and uses it regardless (every deployment reports `builder: DOCKERFILE`), so the `Dockerfile` must stay at the repo root.
  - **Web (`tardbox`):** Dockerfile-based deploy at `https://tardbox.com`. Healthcheck path `/health`; restart policy On Failure; watch paths as below. Every redeploy is ~2 minutes of 502s: the service has a volume, so Railway stops the old container before starting the new one. Railway's `PORT` env var is mapped to `BB_PORT` in the Dockerfile `CMD`. Domain via Namecheap DNS CNAME. Storage is `BB_STORAGE=FS` on an attached Railway volume, not S3.
  - **Bot (`boostr`):** every setting is in the **dashboard**, and there is no file for it — a `railway.bot.toml` once described this service but was never applied, and now cannot be. Start command `java -cp boostbox.jar boostbox.nostrbot`; variable `JAVA_TOOL_OPTIONS` (below); restart policy **Always** (`On Failure` gives up after 10 retries and leaves the bot down with nothing saying so); watch paths `/src/**` `/resources/**` `/deps.edn` `/build.clj` `/Dockerfile`; no healthcheck, since the bot serves no HTTP; one replica, since two would poll the same wallet and race on the same state file, publishing duplicate notes. State is `BB_STORAGE=FS` on a volume at `/data` with `BBN_ALLOW_EPHEMERAL_STATE` set. **The trap:** the Dockerfile `CMD` starts the *web app*, so a bot service without its start command is a second copy of tardbox, and the only symptom is `boostbox.boostbox/app-starting-up` in the logs where `boostbox.nostrbot/bot-starting` should be. That one line is the fastest way to tell which program a service is actually running.
  - **MSP bot (`boostr`, second service):** the same jar and start command as the bot above, reading a **non-isolated, read-only** NWC connection to the node's main wallet (`get_info`, `list_transactions`, `notifications`; no pay), with `BBN_RECIPIENT_NAMES=MSP 2.0`, `BBN_ACTIONS=boost,auto`, `BBN_STATE_KEY=nostrbot/msp-state.json`, its own volume at `/data`, and Boostr_Bot's nsec. It must **not** set `BBN_PUBLISH_PROFILE` — Boostr owns that npub's `kind:0` and `kind:10002`, and a second publisher would overwrite them. Its one-time `BBN_BACKFILL_SEC` must be removed once the first poll lands, for the reason in the state-file note above.
- **Railway bills memory by the minute, and the JVM defaults are wrong for that.** Uncapped, a JVM takes a quarter of the container limit as its heap ceiling and keeps whatever it grows into; locally a burst of homepage renders took one to 3.5 GB resident, and it never came back. Both services therefore carry explicit flags, both with `ExitOnOutOfMemoryError`, because an OOM otherwise kills one thread and leaves a process that looks alive:
  - **Web:** in the Dockerfile `CMD` — `-Xms64m -Xmx512m`, G1 with `G1PeriodicGCInterval` so the heap is handed back after a burst. Setting `JAVA_OPTS` on the service **replaces** them (the command uses `${JAVA_OPTS:-…}`), so include every flag you still want. 512m is sized for the banner's worst case (`banner/max-art-pixels`, ~144 MB decoded); the homepage is cached (above), but a miss still reads and renders every stored boost, so one render's peak grows with the boost count — if the web service starts restarting on OOM, that is the thing to fix (paginate the cards, or keep an index), not the cap.
  - **Bot:** the dashboard variable `JAVA_TOOL_OPTIONS=-Xms32m -Xmx192m -XX:+UseSerialGC -XX:+ExitOnOutOfMemoryError`. The JVM reads that variable itself, so the start command stays a plain `java` with no shell quoting, and it prints `Picked up JAVA_TOOL_OPTIONS: …` as the first log line — which is how to confirm the flags are live. SerialGC because the bot has no bursts to give memory back after, and its bookkeeping is ~55 MB less than G1's.
- **Watch paths limit redeploys to changes that reach the image:** `/src/**` `/resources/**` `/deps.edn` `/build.clj` `/Dockerfile`, set in **both** services' dashboards. A docs-only push used to rebuild twice and redeploy both services, and each web redeploy is an outage; it now shows as `SKIPPED` on both. A new file the image depends on must be added to both lists.
- **Docker:** Multi-stage `Dockerfile` builds an uberjar with `tools.build`, runs on `eclipse-temurin:21-jre-alpine`, plus `freetype`/`fontconfig` for the banner. Also available as `ghcr.io/noblepayne/boostbox:latest`. **Verify the banner in the container, not only on the host** — `curl -o /tmp/b.png 'http://localhost:8080/og/boost.png?title=X&sats=21'` and look at it. A font problem here renders a blank 1200×300 PNG with a 200 status.
- **Nix:** `nix run github:noblepayne/boostbox`
- **NixOS module:** `module.nix` provides a systemd service with hardened settings

### Dependencies (deps.edn)

HTTP: aleph (server + relay websocket client), babashka.http-client (test client, and the bot's BoostBox client). Routing: reitit + swagger. Validation: malli. JSON: jsonista. HTML: chassis. AWS: cognitect.aws. Logging: mulog. IDs: clj-uuid. Crypto: bouncycastle (`bcprov-jdk18on`, secp256k1 for BIP-340 and NIP-04 ECDH — pure Java, so no native libs and it works unchanged on the alpine runtime image).

**Adding a dependency requires regenerating `deps-lock.json`** (`scripts lock`, i.e. `nix flake lock && nix run .#deps-lock`). `nix build` pins every artifact by sha256 and will fail against a stale lock.

Aliases: `:repl` (NREPL + CIDER), `:test` (kaocha), `:test/watch`, `:build` (tools.build uberjar), `:outdated` (antq).
